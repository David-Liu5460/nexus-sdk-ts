HITL（Human-In-The-Loop，人在回路）指在自动化的图执行流程中插入**人工介入点**：流程跑到某个节点时挂起，等待人工决策（审批、补充信息、纠错），人工处理后再从挂起处续跑。nexus-sdk-ts 通过 **中断（interrupt）+ 快照序列化 + 恢复重放（resume/replay）** 实现这一能力。

> 原 Go 版文档 [`4. HITL(Human-In-The-Loop) Node.md`](./original/4.%20HITL(Human-In-The-Loop)%20Node.md) 为空，本文基于 Bun + TS SDK 实际代码从零编写：`src/schema/interruption.ts`（中断状态）、`src/context/context.ts` 与 `src/context/memory.ts`（`interrupt`/`snapshotSession`/`resume`）、`src/core/application.ts`（中断检查与续跑），可运行示例见 `examples/resume.ts`。

---
核心概念

| 概念 | 说明（源码位置） |
| --- | --- |
| `InterruptionState` | 中断状态对象，含 `question` / `currentNode` / `interruptionType` / `isResumed` / `sessionStateSnapshot` 等（`src/schema/interruption.ts`） |
| `InterruptionType` | 枚举：`None`（无）/ `Stop`（已挂起）/ `Continue`（待续跑）（`src/schema/interruption.ts`） |
| `ctx.interrupt(question)` | 在节点内请求挂起，记录待办问题，把中断类型置为 `Stop`（`src/context/memory.ts`） |
| `ctx.snapshotSession()` | 把当前状态 map 快照进中断状态，供序列化与续跑（引擎在挂起时自动调用） |
| `serialize/deserializeInterruption` | 中断状态的 JSON 序列化/反序列化，用于跨进程持久化（`src/schema/interruption.ts`） |
| `ctx.resume(state?)` | 用外部中断状态回填上下文：恢复状态快照、标记 `isResumed`、切到 `Continue` |

---
中断与续跑的执行流程

引擎对中断的处理集中在 `execute`（`src/core/application.ts`）：

1. 每执行完一波节点，检查 `ctx.getInterruptionState()`。
2. 若类型为 `Stop` → 调 `setInterruptionNode` 记录当前节点 + `snapshotSession()` 快照状态，然后**优雅返回**（不报错、不继续）。
3. 之后可把中断状态序列化持久化（落库/Redis/MQ），等待人工处理。
4. 人工处理后，新建/复用 Context 调 `resume(state)`，`invoke` 检测到 `isResumed && Continue` → **从 `currentNode` 重放**，而非从入口重头执行（见 `invoke`，`src/core/application.ts`）。

```
首次执行: entry → ... → review 调 interrupt() → 引擎检测 Stop → 快照 + 返回
              ↓ serializeInterruption(状态可落库)
人工审批: 把审批结果写回 sessionStateSnapshot
              ↓ deserializeInterruption
续跑执行: resume(state) → invoke 从 review 重放 → ship → END
```

---
基础用法：节点内请求中断

在节点函数里，当需要人工介入时调用 `ctx.interrupt(question)` 并返回 `null`（不再往下走）：

```ts
import { gotoNode } from "nexus-sdk-ts";

g.addNode({
  name: "review",
  func: async (ctx) => {
    // 未审批通过 => 请求中断，等待人工介入
    if (!ctx.get<boolean>("approved")) {
      ctx.interrupt("订单 #A1001 需要主管审批，请确认是否放行");
      return null; // 本节点不再往下走，引擎会在中断检查处停下
    }
    // 已审批 => 正常路由到下一步
    return gotoNode("ship");
  },
});
```

> 要点：`interrupt()` 只是把中断类型置为 `Stop` 并记录问题；真正的“停下 + 快照”由引擎在本波执行后的中断检查处完成。所以节点内 `interrupt()` 后应 `return null`，把控制权交还引擎。

---
同进程恢复（最简）

如果不需要跨进程，拿到同一个 ctx 写回人工决策，直接 `resume()` 再跑一次即可：

```ts
import { Graph, MemoryContext, InterruptionType } from "nexus-sdk-ts";

const app = buildGraph().compile();

// 1) 首次执行，跑到 review 挂起
const ctx = new MemoryContext({ query: "下单并发货" });
await app.invoke(ctx);

if (ctx.getInterruptionState().interruptionType === InterruptionType.Stop) {
  console.log("待办:", ctx.getInterruptionState().question);

  // 2) 人工决策写回状态
  ctx.set("approved", true);

  // 3) 就地恢复（不传 state = 用本上下文已有的中断态），从 review 重放
  ctx.resume();
  await app.invoke(ctx);
}
```

---
跨进程恢复（序列化 → 持久化 → 重放）

真实 HITL 场景里，挂起和审批往往发生在不同请求/进程。把中断状态序列化存起来，审批回调时再反序列化恢复。完整流程见 [`examples/resume.ts`](../../examples/resume.ts)：

```ts
import {
  InterruptionType,
  serializeInterruption,
  deserializeInterruption,
} from "nexus-sdk-ts";

// ===== 进程 A：首次执行，跑到 review 挂起 =====
const ctxA = new MemoryContext({ query: "下单并发货" });
await buildGraph().compile().invoke(ctxA);

const itA = ctxA.getInterruptionState();
if (itA.interruptionType !== InterruptionType.Stop) return;

// 序列化中断态（真实场景：写 DB / Redis / MQ，等待人工审批回调）
const blob = serializeInterruption(itA);

// ===== 进程 B：人工审批通过后，凭序列化串恢复并续跑 =====
const restored = deserializeInterruption(blob);
// 把人工审批结果写回状态快照，重放时 review 节点据此放行
restored.sessionStateSnapshot = { ...restored.sessionStateSnapshot, approved: true };

const ctxB = new MemoryContext();
ctxB.resume(restored);                 // 回填快照 + 标记 isResumed + 切 Continue
await buildGraph().compile().invoke(ctxB); // 从 review 重放，而非从 submit 重头执行
```

> 关键：人工决策通过修改 `restored.sessionStateSnapshot` 注入——`resume(state)` 会用这个快照覆盖上下文状态（见 `src/context/memory.ts`），于是重放时 `review` 读到 `approved=true` 并放行。

---
注意事项

1. **`interrupt()` 后要 `return null`**：返回 `null` 让节点不产生路由，引擎才能在本波结束后的中断检查处停下。若返回了 `goto`，下一波仍可能被调度（中断检查在本波之后才执行）。
2. **从中断节点“重放”而非“继续”**：续跑是**重新执行** `currentNode`（不是跳到它的下一个节点）。因此中断节点的逻辑要能根据恢复后的状态走不同分支（如示例中 `review` 用 `approved` 区分挂起/放行），否则会再次触发中断造成死循环。
3. **决策数据走状态快照**：跨进程恢复时，人工结果应写入 `sessionStateSnapshot` 后再 `resume`，因为 `resume(state)` 用快照重建状态 map。同进程则直接 `ctx.set(...)` 再 `resume()`。
4. **`resume()` 的两种用法**：传 `state`（来自反序列化）用于跨进程；不传参数则就地恢复本上下文已有的中断态，用于同进程。两者都会把类型切为 `Continue`、`isResumed=true`。
5. **消息不在快照内**：`snapshotSession` 只快照状态 `state` map（见 `src/context/memory.ts`），不含消息历史。若中断节点依赖消息上下文，跨进程恢复需自行重建消息。
6. **MemoryContext 是参考实现**：内存实现进程退出即丢失，跨进程能力依赖你把 `serializeInterruption` 的结果持久化到外部存储。

相关 API 速览

```ts
// 节点内
ctx.interrupt(question: string): void;          // 请求挂起
ctx.getInterruptionState(): InterruptionState;  // 读取中断态

// 引擎自动调用（一般无需手动）
ctx.setInterruptionNode(node: string): void;    // 记录中断节点
ctx.snapshotSession(): void;                     // 快照状态

// 恢复
ctx.resume(state?: InterruptionState): void;     // 回填 + 标记续跑

// 跨进程持久化
serializeInterruption(s: InterruptionState): string;
deserializeInterruption(raw: string): InterruptionState;
```
